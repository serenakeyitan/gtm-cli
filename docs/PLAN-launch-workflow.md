# Plan: Launch Workflow + Dashboard Integration

**Status:** drafted 2026-04-28, not yet started.
**Goal:** make gtm-cli the single tool for managing a launch tracking repo end-to-end (draft → preflight → submit → engagement sync → dashboard render → deploy), generalized for any user, not hardcoded to atf-launch.

## Why now

Right now the launch flow is split across four tools:
- **atf-launch** (the launch repo) — hand-edited markdown + a hand-edited HTML dashboard
- **gtm-cli** — has identity management + preflight, missing post lifecycle commands
- **Manual Playwright scripts** in `/tmp/fill_d*.py` — one-shot, untracked, not reusable
- **wrangler** — manual `pages deploy` after each dashboard edit

Two problems with that:

1. **Single-user only.** Everything assumes paths under `/Users/keyitan/atf-launch` and `/Users/keyitan/.openclaw-growth-pipeline/secrets/`. Anyone else who wants to use gtm-cli for their own launches has nothing to clone.
2. **State drifts between layers.** A post goes live → engagement comes in → the dashboard's hardcoded numbers are wrong → the recommender lies → the user makes bad decisions.

This plan unifies all four into one CLI that scaffolds, tracks, posts, syncs, renders, and deploys.

## Convention: a "launch directory"

Any directory containing `.gtm-launch.yaml` is a launch directory. Layout:

```
<launch_dir>/
├── .gtm-launch.yaml          marker + config
├── README.md                 user-owned
├── ROADMAP.md                user-owned (cross-product)
├── dashboard.html            generated by `gtm dashboard build`
├── dist/                     deploy staging (gitignored)
└── <product>/
    ├── ROADMAP.md            user-owned
    ├── posts/
    │   ├── <slug>.md         post: frontmatter + body
    │   └── assets/           images
    └── tracking.md           generated by `gtm post sync`
```

`.gtm-launch.yaml`:
```yaml
version: 1
products:
  - key: first-tree
    name: first-tree
    tagline: Shared Context for Agent Teams
    status: active   # active | next | future
  - key: repo-gardener
    ...
directions:
  - key: doc-drift
    label: solve doc drifts
  - key: llm-wiki
    label: llm-wiki
default_identity_by_platform:
  reddit: Pale_Stand5217
  twitter: my-handle
dashboard:
  cloudflare_project: atf-launch     # optional, used by `gtm dashboard deploy`
```

Post frontmatter (the source of truth, no other state):
```yaml
---
id: d1
product: first-tree
direction: llm-wiki
channel: reddit r/AI_Agents
identity: Pale_Stand5217
kind: image | self | link
image: posts/assets/llm-wiki-repo.png   # optional
status: drafting | scheduled | live | removed
url:
live_id:
posted_at:
metrics:
  score: 0
  comments: 0
  comments_real: 0
  last_checked:
note:
---

<post body markdown>
```

## Command surface

| Command | Purpose | E2e hardness |
|---|---|---|
| `gtm launch init [path]` | Scaffold a new launch dir interactively (prompts for name, products, directions) | low |
| `gtm launch link [path]` | Mark an existing dir as a launch dir (writes `.gtm-launch.yaml` from prompts/inferred state) | low |
| `gtm launch info` | Print the current launch dir, product list, direction list, identity defaults | low |
| `gtm post draft <product> --channel <ch> [--direction <d>] [--identity <i>]` | Interactive: title + body editor + image picker → writes `<product>/posts/<slug>.md` (status=`drafting`) | low |
| `gtm post list [--product <p>] [--status <s>]` | Table view of posts | low |
| `gtm post submit <slug>` | Preflight → confirm → Playwright submit → write `live_url`/`live_id`/`posted_at`/`status: live` back to frontmatter | **high** (live network, real account) |
| `gtm post sync [--slug <s>]` | Re-fetch score/comments for live posts; identify bot/OP comments; update metrics + `comments_real` | medium |
| `gtm post status <slug>` | Show frontmatter + last 5 comments | low |
| `gtm dashboard build` | Read all `posts/*.md`, regenerate `dashboard.html` (replace the hand-edited single-file dashboard) | medium |
| `gtm dashboard deploy [--provider cloudflare\|vercel]` | Deploy `dashboard.html` to the configured provider | medium |
| `gtm dashboard serve [--port 8080]` | Local preview server | low |

## Checkpoint plan (8 CPs, each with scoped e2e)

### CP1: launch directory model + `init` / `link` / `info`
- New module `gtm/launch/__init__.py` — `LaunchDir` dataclass, finds `.gtm-launch.yaml` walking up from cwd or via `--launch <path>`
- `gtm launch init` prompts and scaffolds full dir tree
- `gtm launch link` is the same but for an existing dir (atf-launch's case — needs to not clobber existing files)
- `gtm launch info` prints config
- E2e: scaffold a tmp dir, link it, info prints expected
- **Validation milestone:** `gtm launch link /Users/keyitan/atf-launch` works without overwriting anything

### CP2: post frontmatter parser + `gtm post list/status`
- `gtm/launch/post.py` — `Post.load(path)`, `Post.save(path)`, frontmatter validation
- `gtm post list` reads all posts, prints sortable/filterable table
- `gtm post status <slug>` prints one post's metadata
- E2e: synthetic launch dir with 3 posts → list/filter/status all work
- **Validation milestone:** `gtm post list --launch /Users/keyitan/atf-launch` shows the 6 real posts (3 doc-drift + 3 llm-wiki)

### CP3: `gtm post draft` (interactive create)
- Click prompts for title, body (opens `$EDITOR`), channel inference (sub auto-detected from `r/<sub>` channel string), identity (default from config), kind (text/image/link), image path
- Writes `<product>/posts/<slug>.md` with `status: drafting`
- Slug auto-generated: `<YYYY-MM-DD>-<sub>-<short-title>`
- E2e: subprocess + canned input → file written with expected frontmatter
- **Validation milestone:** drafting a fake llm-wiki post for r/LangChain in atf-launch produces a clean .md

### CP4: `gtm post submit` (the load-bearing one)
- Reads post .md → confirms (`Submit "<title>" to <sub> from <identity>?`) → calls preflight → bails on FAIL
- Playwright submit (text/image/link kinds) using the post's identity's session
- On success: writes `live_url`/`live_id`/`posted_at` + bumps `status: live`
- On failure: leaves status, writes `note: "submit failed: <reason>"` so it's visible in dashboard
- E2e: dry-run mode (`--dry-run`) that goes through preflight + page-open but stops before clicking Submit. Real submit is manual gate.
- **Validation milestone:** `gtm post submit d1 --dry-run` opens browser to r/AI_Agents pre-filled

### CP5: `gtm post sync` (engagement refresh + bot filtering)
- Hits `https://reddit.com/comments/<id>.json` for every live post
- Updates `metrics.score`, `metrics.comments`
- Computes `metrics.comments_real` by excluding `AutoModerator` + the post's own `identity` (the bot/OP problem we just hit)
- Updates `metrics.last_checked` to ISO timestamp
- E2e: mock the JSON endpoint, verify the right posts get updated and bots are filtered out
- **Validation milestone:** sync against atf-launch's 6 real posts produces same numbers we just hand-fetched

### CP6: `gtm dashboard build` (HTML render from frontmatter)
- New template `gtm/launch/dashboard_template.html` based on the current `atf-launch/dashboard.html` (extract the React component)
- Build reads `.gtm-launch.yaml` + all post .md files → renders into the template
- Output: `<launch_dir>/dashboard.html` (overwrite OK — it's generated)
- The recommender JS stays inline, fed by the rendered POSTS array
- E2e: build against the synthetic launch dir → output validates against expected HTML structure
- **Validation milestone:** `gtm dashboard build --launch /Users/keyitan/atf-launch` produces an HTML file that matches the current hand-edited one (modulo whitespace)

### CP7: `gtm dashboard deploy` + `gtm dashboard serve`
- `serve` runs `python -m http.server` on the launch dir
- `deploy --provider cloudflare` shells to `wrangler pages deploy <dist>` after staging the HTML to `dist/index.html`
- `deploy --provider vercel` likewise via `vercel deploy`
- Provider config from `.gtm-launch.yaml`
- E2e: `serve` smoke-tests the local URL responds 200; `deploy --dry-run` prints the wrangler command without running it
- **Validation milestone:** `gtm dashboard deploy --launch /Users/keyitan/atf-launch` redeploys to atf-launch.pages.dev

### CP8: end-to-end smoke + onboarding doc
- `tests/e2e/test-launch-workflow.sh` — full flow against a tmp launch dir: init → draft → list → (mock submit) → sync → build → serve → asserts the dashboard renders the post
- `docs/LAUNCH-ONBOARDING.md` — "10-minute getting started" doc:
  1. `gtm auth reddit --username <u>` (existing) registers identity
  2. `gtm launch init my-launches` scaffolds the dir
  3. `gtm post draft my-product --channel "reddit r/foo"` writes a draft
  4. `gtm post submit <slug>` posts it
  5. `gtm dashboard build && gtm dashboard deploy` ships the tracker
- **Validation milestone:** a fresh-clone teammate can follow the doc and post their first launch in under 15 min

## Out of scope (explicit non-goals)

- **Multi-user collaboration on the same launch repo.** First-tree-style ownership/PR review can come later. For now, one user per launch dir.
- **Auto-posting (no human gate).** Every `submit` requires explicit confirm. We're not building a fire-and-forget bot.
- **Scheduled posting.** No cron. If you want delayed posts, that's `at` or a calendar reminder for now.
- **Twitter/HN parity in CP1-8.** This plan is Reddit-only. Twitter follows the same shape (we already have `twitter_browser_post` in `gtm.platforms.twitter`); add as CP9-10 in a follow-up.
- **Cross-launch-dir aggregation.** Each launch dir is independent. No "show me all launches across all my projects" view.

## Open questions (decide before CP1)

- **Q1:** atf-launch already has `dashboard.html` hand-edited with a recommender + 6 real posts. When `gtm launch link /Users/keyitan/atf-launch` runs CP1, should it: (a) leave dashboard.html alone until first `gtm dashboard build`, or (b) parse the existing posts out of the HTML and write them as .md files? **Default: (a)** — user runs `gtm post import-from-dashboard` as an opt-in one-shot if they want.
- **Q2:** Where does the dashboard React component live in gtm-cli? Inline in a `.html` template, or as a `.tsx` file we bundle with esbuild at install time? **Default: inline `.html` template** (no build step, matches current dashboard).
- **Q3:** Should `gtm post draft` open the editor with a starter template (lowercase voice rules pre-filled) or just blank? **Default: starter template** with comment markers like `<!-- karpathy-voice: lowercase, no em dashes, "i" not "we" -->`
